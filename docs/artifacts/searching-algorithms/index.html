Searching: Linear and Binary Search

How to find an item in a list. Linear search checks every item in turn. Binary search throws away half the list each time, but only works on sorted data. Trace both, race them, and practise the questions that come up in Paper 4.

The big idea

A searching algorithm finds the position of a target value in a collection of data, or reports that it is not there. The two you need are linear search and binary search. The choice depends on whether the data is sorted, and how big it is.

Linear search

Start at the first item and compare each item with the target, one after another, until you find it or run out of items.

  • Works on unsorted or sorted data.
  • Best case: target is the first item, 1 comparison.
  • Worst case: target is last or missing, n comparisons.
  • Simple to write. Slow on big lists.

Binary search

Look at the middle item. If it is the target, stop. If the target is bigger, discard the lower half; if smaller, discard the upper half. Repeat on what is left.

  • The list must be sorted first.
  • Best case: target is the middle item, 1 comparison.
  • Worst case: about log₂ n comparisons.
  • Very fast on big lists. Needs direct access by index.

Binary search in four moves

MoveWhat happensPseudocode
1 · BoundsLow is the first index, High is the last.Low ← 0, High ← N - 1
2 · MiddleFind the midpoint with integer division.Mid ← (Low + High) DIV 2
3 · CompareEqual: found. Item at Mid too small: target must be above. Too big: target must be below.IF Data[Mid] = Target
4 · ShrinkMove one bound past Mid, then repeat. Stop when Low > High (not found).Low ← Mid + 1 or High ← Mid - 1
Classic bugSetting Low ← Mid or High ← Mid (instead of Mid + 1 and Mid - 1) can loop forever, because Mid is already known not to be the target.

How fast does it grow?

Every comparison in binary search halves the list. So doubling the list size adds only one extra comparison in the worst case. A list of 1,023 items needs at most 10 comparisons; 1,048,575 items need at most 20. Linear search needs up to a million. This is the idea behind order of growth: linear search is O(n), binary search is O(log n) (see 19.1.5).

maximum comparisons for binary search = ⌊log₂ n⌋ + 1

5 · Multiple choice

Descriptions are kept general. Use them as examples of ideas, not as exact descriptions of any company's software.

Phone contacts

Your contacts are kept sorted by name. Typing a name jumps to it quickly rather than scanning from the top, which is the binary-search idea of repeatedly discarding half of the sorted list.

Exam use: an example of a large sorted list that is searched often, where binary search beats linear search.

Database indexes

Databases keep an index of a column in sorted order so a query for one customer ID does not read every row. Real indexes often use tree structures, which build on the same halving idea.

Exam use: why sorting once and searching many times can pay off.

Finding the commit that broke the code

Version control tools include a bisect feature. Given a good version and a bad version, it tests the version halfway between them, then halves again, until it finds the first bad one.

Exam use: shows that binary search is about halving any ordered range, not only arrays of numbers.

Scanning an unsorted log

A server log is written in the order events happen, not sorted by error type. To find the first line containing "ERROR" the program just reads down the file.

Exam use: linear search is the right choice when data is unsorted and sorting it would cost more than one scan.

Guess the number

In a game where someone thinks of a number from 1 to 100 and says "higher" or "lower", guessing the middle each time finds it in at most 7 guesses.

Exam use: a quick way to explain log₂ n: 2⁷ = 128 ≥ 100.

A short shopping list

With 8 items you would just read down the list. Setting up a sort and a midpoint calculation would be more work than it saves.

Exam use: binary search is not always the better choice. For small or constantly changing lists, linear search can be the sensible answer.

Exam-style questions

Open each question for reminders, a model answer and common mistakes. Each coloured phrase earns one mark; the number shows which mark point it is.

Q1 State 2 marks State two differences between a linear search and a binary search.
ReminderGive two separate differences, not one difference said twice. Sorted data is the one examiners most want.
A binary search requires the data to be sorted, whereas a linear search works on unsorted data. A linear search checks items one at a time from the start, whereas a binary search repeatedly checks the middle item and discards half of the remaining data.
Common mistakeWriting "binary is faster" with no detail. Speed is a result of the method; the question asks about differences in how they work.
Q2 Describe 4 marks Describe how a binary search finds a value in an ordered array.
ReminderDescribe the loop in order: bounds, middle, compare, discard, repeat, stop.
The lowest and highest index of the array are used as the bounds. The middle index is found. The value at the middle is compared with the target. If they are equal, the search stops, because the item has been found. If the target is greater than the middle value, the lower half (up to and including the middle) is discarded; if it is smaller, the upper half is discarded. The process repeats on the remaining half, until the item is found or no items remain (low is greater than high), so the item is not in the array.
Common mistakeForgetting the stopping condition for a value that is not in the array.

Q4 Explain 3 marks Explain why a binary search is usually faster than a linear search on a large list.
ReminderSay what binary does each time, then the effect on the number of comparisons, then a comparison with linear.
A binary search discards half of the remaining items after every comparison. So the number of comparisons grows very slowly as the list gets bigger (about log₂ n in the worst case). A linear search may have to check every item, so in the worst case it needs n comparisons.
Common mistakeForgetting the sorted-data condition. It is worth adding that binary search only gives this benefit if the list is already sorted.

Q6 Calculate 2 marks A sorted array contains 1,023 items. State the maximum number of comparisons a binary search needs, and show how you worked it out.
ReminderKeep halving: 1023 → 511 → 255 → ... Count how many halvings until one item is left, then add the final check.
2¹⁰ = 1,024, so 1,023 items can be halved 10 times (or ⌊log₂ 1023⌋ + 1) Maximum = 10 comparisons.
Common mistakeAnswering 1,023 ÷ 2 = 511 or giving log₂ 1,023 as 9.99 with no whole number.
Q7 Discuss 4 marks A shop has an array of 12,000 product codes, sorted in order, which is searched thousands of times a day. New products are added once a week. A programmer suggests using a linear search because it is simpler. Discuss whether this is a good choice.
ReminderUse the scenario. Give a point for linear, a point against, and a judgement.
A linear search is simpler to write and works without the data being sorted. However the array is already sorted, so a binary search can be used with no extra sorting cost. With 12,000 items, a linear search could need up to 12,000 comparisons per search, whereas a binary search needs at most 14, and the shop searches thousands of times a day. So binary search is the better choice; the code is a little more complex but it only has to be written once, and the list only needs re-sorting weekly when products are added.
Common mistakeA general comparison of the two searches that never mentions the scenario figures (12,000 items, sorted, weekly updates).
Q8 Write 6 marks Write a function BinarySearch(Data, Target) that returns the index of Target in the sorted array Data, or -1 if it is not found. Use Python or pseudocode.
ReminderSix marks means six features: bounds, loop condition, midpoint, comparison, both bound updates, return values.
def binary_search(data, target):
    low = 0                          # (1) bounds set
    high = len(data) - 1
    while low <= high:               # (2) loop condition
        mid = (low + high) // 2      # (3) integer midpoint
        if data[mid] == target:      # (4) comparison, return index
            return mid
        elif data[mid] < target:
            low = mid + 1            # (5) discard lower half
        else:
            high = mid - 1           # (5) discard upper half
    return -1                        # (6) not found

Low and high initialised to the first and last index. Loop while low <= high. Mid is the integer midpoint. If data[mid] equals the target, the index is returned. Low = mid + 1 or high = mid - 1 as appropriate. -1 is returned when the loop ends.

Common mistakeUsing / instead of // in Python, which gives a float and causes a TypeError when used as an index.

Top tips

  • Say "sorted" every time. Any answer about binary search should mention the data must be in order.
  • Trace with a table. One row per loop: Low, High, Mid, Data[Mid]. Marks follow the rows.
  • Midpoint uses integer division. (Low + High) DIV 2. Round down, never up.
  • Move past Mid. Low ← Mid + 1 and High ← Mid - 1. Using Mid itself can loop forever.
  • Check the lower bound. This artifact uses 0, but many CIE questions start arrays at 1.
  • Count the max comparisons by halving. n items need ⌊log₂ n⌋ + 1 comparisons at most.
  • Compare with the scenario. "Binary search is faster" earns little; "12,000 sorted items searched often" earns marks.
  • Linear search is not "bad". For small, unsorted, or constantly changing data it is often the right choice.
